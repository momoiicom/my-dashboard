# Browser notifications

People opt in for each browser through Account menu → Notifications → Enable notifications. The browser asks for permission only after that click. The bot may then mark an important changed update with `notify=true` on the existing card PUT. Notifications contain a generic message and link to the board. Card titles and document content never enter the push payload or lock-screen notification.

Set `PUSH_VAPID_PUBLIC_KEY`, `PUSH_VAPID_PRIVATE_KEY`, and `PUSH_VAPID_SUBJECT` in the server environment. Generate one persistent pair with `node -e 'console.log(require("web-push").generateVAPIDKeys())'`. The subject is a `mailto:` contact or HTTPS URL. Back up the private key and keep it outside source control. Apply Prisma migrations before enabling registration. Web Push requires a secure browser context; localhost is accepted for local testing. iOS support requires adding the site to the Home Screen.

`GET /api/push` gives the signed-in browser configuration, owner ID and hashes of its registered endpoints without revealing endpoints. `POST` registers one browser subscription; `DELETE` removes it. Writes require a browser session, JSON and matching Origin. A bot token cannot register devices or choose recipients. A subscription endpoint belongs to one account and each account has at most ten subscriptions. Registration accepts HTTPS endpoints from documented FCM, Mozilla and Apple push-service hosts. This restriction blocks arbitrary outbound requests. Providers are grounded in [Chrome FCM guidance](https://web.dev/articles/codelab-notifications-push-server), [Mozilla device registration](https://mozilla.github.io/ecosystem-platform/relying-parties/how-tos/device-registration/), and [Apple Web Push guidance](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers).

The card write commits before push requests begin. Requests have a three-second deadline, no redirects, and a five-minute provider TTL. The receipt reports provider acceptance; it cannot promise display. A process crash after commit may lose the notification, and an identical retry will not resend. Expired 404/410 subscriptions are removed conditionally. Other provider failures leave the subscription for a future update.

The service worker checks the current session and subscription before choosing a board target. If that check fails or the account changed, it still shows a generic dashboard notification targeting `/`, as [WebKit requires a visible notification for every received push](https://webkit.org/blog/12945/meet-web-push/). Sign-out tries to remove and unsubscribe the current browser after pending card edits flush. Push cleanup is bounded to four seconds so an unavailable push service cannot prevent sign-out. A stale provider message can still produce a generic notification; it exposes no former account details.

Run `npm run build`, then `npm run test:push` for isolated HTTP verification or `npm run test:push:browser` for the rendered browser and service-worker checks. The scripts create and remove a temporary SQLite database and start a loopback server. HTTP delivery uses real encrypted request generation with a local provider-response fixture. Browser enrollment uses a simulated PushManager and Chromium permission grant; push events arrive through CDP and use the registered worker's real `showNotification`. Notification-click tests use a synthetic event and verify actual same-origin client navigation; native focus requires a trusted user event and remains unverified. These checks do not prove native provider enrollment or operating-system display. Screenshots are saved under `.e2e/push/`. A configured HTTPS deployment and real device remain necessary for that acceptance check.
